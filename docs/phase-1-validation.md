## 先提出的问题

对每篇文章先问四件事：

1. **读到的到底是哪一层文本？** 是原创论述、译编、对另一项目/论文的转述，还是正文与作者笔记混合？每个关键观点归谁？
2. **文章要解决什么任务？** 是解释机制、提供可操作步骤、报告一次观察、比较概念，还是帮助做决策？它宣称的结果属于哪一种？
3. **支撑达到哪一步？** 文本给出方案、代码、预期输出、作者报告的实际结果、可查记录，还是独立复现？这些材料足以支持描述性、因果性或迁移性结论吗？
4. **下一步只核对什么？** 选一项会改变理解或决策的缺口，明确需要原始论文、官方文档、运行记录、用户数据或反例中的哪一种证据。

| 领域/功能 | 细化的阅读问题 | 不应跨越的推断 |
| --- | --- | --- |
| Agent 方法与评测 | 改的是模型、执行 harness，还是改进 harness？比较在同一任务、同一模型和环境下进行吗？作者报告的是行为变化、正确性，还是跨任务收益？ | 行为对比、内部评选或少量 benchmark 增益不能单独保证新任务正确或可迁移。 |
| 技术教程与 PoC | 依赖版本、输入、命令、预期输出和实际运行证据各是什么？失败条件与未覆盖范围是什么？ | 代码块、成功标准或文中打印的输出不等于本次独立复现。 |
| 知识建模与架构比较 | 两套术语各自解决什么问题、适用边界在哪？对应关系是标准定义还是作者的架构综合？ | 相似名称不能推出一一对应或互相替代。 |
| 产品/商业方法 | 工作坊的直接产物是什么？客户验证与市场结果分别在哪个阶段取得？案例和总体成功率有无可检查来源？ | 达成团队共识或提出假设不等于假设为真或产品成功。 |
| 译编/二次整理 | 原作者主张、译编者解释、实践补充和外部核对能否分开？ | 译编者的工具推荐不能自动归给原作者。 |

这些问题是对现有篇章结构、论证要素和文本/背景区分的领域化运用，不是新的固定评分表。Harness² 论文自己明确说，行为对比用于指导修改而不验证任务正确性；论文也报告了退化案例与额外推理成本。这给“先看证据能支持哪种结论”提供了一个具体技术实例，不能据此声称本 Skill 已获实验验证。

## 人工应用新版规则：可复核的短答

**Harness² README。**【README 陈述】项目要解决新任务没有正确答案反馈时如何改进执行 harness，以及如何把一次任务中的改进经验用于后续任务；方法分任务内的提议、试跑、组合与跨任务经验更新。README 报告的是三个 benchmark、四种模型与 harness 配置下的结果，没有提供传统单篇文章的署名和发布日期；仓库页面会变化，本次阅读没有固定提交版本。【外部核对】[论文第 2.2.1 节](https://arxiv.org/html/2610.14224v1)说明同一任务、匹配模型和环境下的执行对比只提供行为证据，不验证答案正确；[实验与局限](https://arxiv.org/html/2610.14224v1)报告三次运行的均值和标准差、九个退化例及额外推理成本。【推断】它适合启发“依据可观察失误修改并复测”的 Skill 改进流程，却不能让本次人工试读自动获得论文 benchmark 的效度。【未知】在当前文章阅读任务上是否有稳定增益，尚无独立重复运行数据。

**12-Factor Agents 译编。**【本文陈述】开头说明内容来自 HumanLayer，并加入个人实践笔记；“采用 BAML”写在第 2 项的“理解笔记”里。【判断】复述时应说“本文作者补充建议考虑 BAML”，不写成“HumanLayer 的第二原则要求 BAML”。【未知】上游其他位置是否讨论 BAML，本次没有单独核对。

**cognee PoC。**【本文陈述】第 3.1 节列出多格式入库、联合检索、agent 调用的目标、四条成功标准，以及明确不验证的范围；后面给出实现代码与排错。【判断】可把它读成可执行的验证方案与实现讲解；已读正文没有可核查的实际运行日志，因此不声称三个目标已由本文实测达到。【下一步核对】若读者要决定是否采用方案，应运行给定输入并保存入库、查询与 agent 回答记录。

**Foundation Sprint。**【本文陈述】工作坊约 10 小时产出“创始假设”，“重要提醒”段落明确说仍是假设，后续 Design Sprint 要做用户测试。【判断】方法可以用于形成共识与待检验方向；文中单个收购故事及“数百项目验证”的表述，缺少足以判断产品成功因果效应的数据。【下一步核对】若要据此投入项目，应先定义要测的用户行为与决策阈值，再看本地客户证据，而非把工作坊产物当市场结论。

**缺失正文。**尝试访问 `https://example.invalid/not-an-article` 得到不可访问结果。合格短答是：“目前无法读取正文，因此无法还原作者观点；请提供正文或可访问的文章链接。”标题、摘要或 URL 字面内容不构成替代证据。

## 追加用例：结语到核心要点（2026-10-21）

材料：[《QQ音乐 Harness Engineering 实践》](https://developer.cloud.tencent.com/article/2671876?policyId=1004)。上一轮试读能还原治理层和证据边界，但遗漏了作者在结语中给出的中心表达，也没有逐项用正文解释“门禁、三层知识、服务矩阵、经验沉淀、单一真相源”。用户指出这个具体缺口，作为本次阅读行为修改的基线失败。

验收输入 A：全文，要求通俗、精炼地理解文章。预期输出应先给出作者的中心结论，再把结语的关键短语回接到正文，分别说清**它是什么、怎样发挥作用**；只取有用的少数要点，不把术语原样重排成另一张口号清单。仍要用一句话标明“更稳、更快”等效果未由文中前后对比数据独立证明。

验收输入 B：只给用户贴出的结语，不给正文。可提取作者明说的中心结论和四项主张；三层目录分别装什么、服务矩阵有哪些字段、门禁怎么验收则应标成正文缺失，不能从常识补写。完整论文、书籍及写作请求仍不触发此 Skill。

人工复测 A（全文，压缩输出）：

> **中心意思（基于作者结语的转述）：**复杂团队要让 AI 稳定交付，就要先说明需求和业务约束，把检查点与团队经验做成可复用的工程文件。
>
> - **门禁：**编码前检查需求是否明确、设计是否覆盖服务与接口契约；进入开发再核查任务拆分与跨仓分支，尽早发现会导致返工的问题。
> - **三层知识与服务矩阵：**分别存放团队通则、研发流程、具体服务知识；矩阵写明服务归属、依赖、仓库路径及是否涉及 IDL，让 AI 知道去哪改、会影响谁。
> - **Knowledge as Code 与 Self-Refinement：**把规范和经确认的重复性教训写成可审查、可版本化的文件，供后续任务复用。
> - **单一真相源与占位符词典：**流程、服务关系和路径变量各有统一定义，避免不同工具或文件各说一套。
>
> **界限：**文中展示了结构和修订示例，没有给出门禁实施前后的返工率或交付周期对比。

人工复测 B（只有结语）：能复述“早拦错、补上下文、沉淀经验、统一口径”四项主张；对三层分别装什么、服务矩阵字段和门禁检查条件，回答“这段未说明，需看正文”，不使用 A 中读到的细节。此项是人工按规则模拟的缺失信息场景，不是多次独立模型运行。

再以 `2025-10-05-Foundation-Sprint.mdx` 交叉检查：可用作者关于“创始假设仍是假设”的明确总结作中心，再简述工作坊形成假设、后续 Design Sprint 做用户测试；无需强制凑四条要点，也不能把工作坊完成写成市场验证完成。

实际触发语境也不同：QQ 音乐用“先读 Skill、提炼中心句、展开指定术语、仅依据正文”的完整提示词；Personal Agent 沿用同一提示词却未替换指定术语，因而必须检测焦点不匹配；《金刚经》只说“这篇文章”并附新文件，依赖同一会话中的阅读目标继续分析。`README.md` 给出可复制的**通用**提示词和可选关注句，而不是要求用户每换一篇文章都手写一套领域词表。

由此得到两条可迁移的检查：**结语若只讲某个分支，不应取代全文主线；用户沿用旧提示词时，不应把旧术语强套到新文章。**两条已写入 `SKILL.md` 的相应阅读步骤。快速阅读和指定关注点的提示词示例放在 `README.md`，不放进运行入口，以免样例主题影响其他文章。

## 验证方式和限制

本轮用上述真实正文做人工逐项试读：检查能否复述中心问题、区分观点归属和证据阶段，并对每篇只提出有针对性的外部核对问题。`quick_validate.py` 结构检查通过；触发描述继续排除书籍、完整论文及写作请求。不可访问 URL 的实际读取失败，上面的短答没有填造内容。人工试读只能说明规则是否清楚、能否产出受原文约束的样例判断，不能测出 Skill 在不同模型或重复运行中的稳定性。后续若要测稳定性，需要固定输入、记录多次独立运行的输出，并由人盲评事实归属与过度推断。
